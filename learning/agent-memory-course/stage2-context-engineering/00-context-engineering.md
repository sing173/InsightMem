# 00 什么是上下文工程

> 阶段入口：[Agent Memory 实战教程](../README.md) · 下一章：[01 ContextBuilder：把候选信息变成上下文](01-context-builder.md)
> 对应 Hello Agents 第 9 章的 9.1–9.2：什么是上下文工程、为什么重要。

## 本章你会得到什么

- 一个 context engineering 的工作定义；
- 一张“上下文由什么组成”的结构图；
- 一个跨天代码库维护场景；
- 阶段一记忆/检索与阶段二上下文管理之间的承接关系。

## 先看一个具体问题

假设你让 Agent 维护一个代码库，任务持续三天：

```text
第一天：探索项目结构，记录潜在问题
第二天：深入某个模块，修复 blocker
第三天：回顾进展，规划重构
```

如果每次请求都把完整聊天历史、全部文件、全部检索结果和全部笔记塞进去，会遇到四个问题：

1. **装不下**：上下文窗口有限；
2. **看不清**：关键约束淹没在噪声里；
3. **会遗忘**：旧摘要可能丢掉重要细节；
4. **难复现**：不同请求看到不同上下文，无法判断行为为何变化。

上下文工程就是解决这些问题的方法：**主动决定什么信息、以什么结构、在什么时间进入模型上下文。**

## 工作定义

> **上下文工程是围绕模型当前任务，设计信息的收集、选择、组织、压缩和注入方式的工程实践。**

它不等于：

- 只写一个更长的 system prompt；
- 只做 RAG；
- 只把聊天历史截断；
- 只追求塞进更多 token。

RAG 和 Memory 负责提供候选信息；ContextBuilder 负责把候选变成本次可用的上下文。

```text
Memory / RAG / Tools / Notes
          │
          ▼
      ContextBuilder
          │
          ▼
  有限、有序、可解释的上下文
          │
          ▼
      Agent / Reader
```

## 有效上下文的“解剖学”

一次请求的上下文通常包含多个来源：

| 来源 | 例子 | 主要风险 |
|---|---|---|
| System instructions | 角色、规则、安全约束 | 过长、冲突、被覆盖 |
| User query | 当前问题与目标 | 模糊、范围漂移 |
| Conversation history | 之前几轮消息 | 噪声、重复、过时 |
| Memory | 用户偏好、事实、经验 | 错误固化、串扰 |
| Retrieved evidence | 文档、代码、日志 | 漏召回、预算挤占 |
| Tool results | 命令输出、API 响应 | 过长、格式混乱 |
| Notes | 任务状态、blocker、action | 陈旧、重复、权限不清 |

上下文工程要同时决定：

- 哪些来源启用；
- 每个来源的优先级；
- 怎样排序和分组；
- 怎样去重和压缩；
- 怎样保留来源与版本；
- 怎样验证预算和权限。

## 三个常见误区

### 误区 1：上下文越长越好

更多信息可能提高覆盖率，也可能增加噪声、成本和冲突。关键是**相关性、结构、顺序和预算**，不是 token 总量。

### 误区 2：检索到就等于用上

候选证据可能被过滤、去重或预算挤掉。必须保存“候选 → 选中 → 注入”的链路。

### 误区 3：摘要就是压缩

摘要只是压缩的一种。上下文工程还包括选择、结构化、排序、去重、分页和工具按需探索。

## 长程任务为什么更难

长程任务跨多个请求，状态会不断变化：

```text
探索 → 记录 → 分析 → 行动 → 检查 → 更新计划
```

每一步都会产生新信息：

- 文件路径与代码片段；
- 工具输出；
- 错误与 blocker；
- 已完成事项；
- 下一步计划。

如果只靠聊天历史，Agent 很容易重复探索、忘记约束或误报进度。Hello Agents 第 9 章因此引入：

- **ContextBuilder**：构建有限上下文；
- **NoteTool**：保存结构化任务状态；
- **TerminalTool**：按需探索文件系统；
- **长程智能体**：把三者组合成跨天工作流。

## 一个最小上下文示例

假设当前任务是“修复 parser 模块的 500 错误”。合理上下文可能包括：

```text
1. 当前任务与验收标准
2. 用户约束：不要改公共 API
3. 当前 blocker：parse_path 丢失反斜杠
4. 相关代码：parse_path 与调用点
5. 最近测试失败输出
6. 已完成步骤：已复现、已定位
7. 下一步：修改并运行测试
```

不相关的历史聊天、其他模块文件、重复日志不必进入本次上下文。

**核心思想：** 上下文不是原始信息的仓库，而是为当前决策加工出来的产品。

## 阶段一怎样承接阶段二

阶段一已经提供了两类原料：

- `email-agent`：记忆的写入、检索、注入与使用归因；
- `InsightMem`：Add/Search、混合召回、证据选择和原始产物。

阶段二不再重复造记忆库，而是新增一个协调层：

```text
阶段一：产生候选与证据
阶段二：选择、组织、压缩并注入上下文
```

当前仓库没有 ContextBuilder、NoteTool、TerminalTool 或 memory OS 实现。因此阶段二代码均标为**教学骨架**，不会把 Hello Agents 的 API 当成本仓库已有能力。

## 本章小结与下一步

你已经理解上下文工程的目标：让模型在有限预算内看到**当前最需要、结构最清晰、来源可追溯**的信息。

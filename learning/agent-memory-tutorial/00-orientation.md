# 00 定位与概念：什么算 Agent 记忆

> 前置：无 · 下一章：[01 边界与地图](01-boundaries.md)
> 预计：3–4 小时
> 本章目标：能定义记忆、画出完整生命周期、区分四种类型和四层结构，并用统一指标判断一个系统是否真的有“记忆”。

---

## 0.1 这份教程要解决什么

学习 agent memory 最常见的三个误区：

1. 把它当成“更长的上下文窗口”；
2. 把它当成“向量数据库 + RAG”；
3. 只看框架 README 的功能列表，不追问写入什么、丢失什么、怎么评测。

本教程用一个固定骨架拆所有系统：**写入 → 组织 → 检索 → 使用 → 治理**。每一步都问四个问题：存什么、何时写、怎么取、错了怎么修。学完你应该能读懂任何一篇记忆论文或一个记忆框架，并判断它的适用边界。

先建立判断标准，再学具体策略。否则很容易把“能存”“能搜”“能摘要”误认为“有完整记忆能力”。

### 0.1.1 两阶段学习路线

本教程按两门社区经典课程组织，但不复制课程目录：

| 阶段 | 主问题 | 对应课程 | 本教程产出 |
|---|---|---|---|
| 阶段一：LangGraph 长时记忆工程 | 如何把语义、情景、程序记忆写入 Store，并检索、装配、更新和评测 | [Long-Term Agentic Memory With LangGraph](https://www.deeplearning.ai/short-courses/long-term-agentic-memory-with-langgraph/) | 带长期记忆的邮件 Agent |
| 阶段二：LLM as Operating Systems | Agent 如何自主管理有限上下文与外部记忆，处理 memory pressure、自编辑、dreaming 和共享 | [LLMs as Operating Systems: Agent Memory](https://www.deeplearning.ai/short-courses/llms-as-operating-systems-agent-memory/) | 可评测的 memory OS mini service |

阶段一回答“记忆作为数据系统怎样做对”；阶段二回答“Agent 怎样主动管理这些记忆”。两者不是替代关系：LangGraph Store 可以成为外部记忆，MemGPT/Letta 的 memory manager 也可以包装 Store、文件或向量库。

### 两个贯穿全教程的项目

**项目 A：邮件 Agent。** 它先做三件事：判断邮件应忽略、通知还是回复；调用日历工具；代写邮件。没有记忆时，它不知道用户的写作风格、会议偏好和过去的承诺。阶段一依次加入：

```text
semantic memory    → 用户事实与偏好
episodic memory    → 历史邮件处理示例
procedural memory  → 从反馈更新的写作与路由指令
```

**项目 B：memory OS。** 它把有限上下文看成工作区，把 Recall Storage 看成完整消息历史，把 Archival Storage 看成长文档库。阶段二依次加入：

```text
core memory        → 当前常驻事实与指令
recall memory      → 可搜索的完整对话
archival memory    → 可搜索的外部知识
memory manager     → 摘要、换入换出、自编辑与共享
```

每个项目都按同一顺序验收：**基线失败 → 单机制改善 → 失败案例 → 成本 → 可复现实验**。

## 0.2 一个可操作的定义

本文采用 [Anthropic 的工程定义](https://www.anthropic.com/research/components-of-agent-memory)与 [LangGraph Memory 中文译文](../../docs/langchain-memory-zh.md)中的工程视角：

> **Agent Memory 是从经验中获得、跨会话保留、以后可以作为上下文重新读取的外部知识。**

这个定义包含四个必要条件：

| 条件 | 要回答的问题 | 不满足的例子 |
|---|---|---|
| 持久性 | 会话结束后状态还在吗 | 只在本次 prompt 里拼接历史 |
| 可读取性 | 以后能按需取回吗 | 写进一个永远无法查询的黑盒日志 |
| 作用域 | 谁可以读、谁不能读 | 所有用户共享一个全局列表 |
| 生命周期 | 如何更新、失效和删除 | 只追加，旧事实永远有效 |

因此，**“保存文本”不等于“实现记忆”**。一个记忆模块至少要有写入契约、读取契约和治理契约。向量数据库只是其中一种组织与检索工具。

### 用状态转移而不是组件名称定义记忆

可用一个最小模型描述每次交互：

```text
M(t+1) = Write(M(t), event(t))
context(t+1) = BuildContext(M(t+1), query(t+1), budget)
action(t+1) = Agent(context(t+1), tools)
```

`Write` 可能追加原文、抽取 fact、更新规则，或选择不写。`BuildContext` 才决定哪些记忆真正进入推理。**写入成功但从未进入上下文，不会改善答案。**

### 三种正交分类

分类时把三个问题分开，避免把“短期”当成存储位置：

| 维度 | 选项 | 回答的问题 |
|---|---|---|
| 内容类型 | 工作、情景、语义、程序 | 记的是哪类知识 |
| 可恢复范围 | 单次请求、单线程、跨会话、跨用户授权范围 | 谁在什么时候能恢复 |
| 生命周期 | 临时、活跃、失效、归档、删除 | 记录如何随时间变化 |

工作记忆指决策周期中正在使用的变量；短期记忆通常指有限时间或有限范围的状态。两者经常重叠，但不是同义词。

### 记忆不是模型权重

- 记忆：外部、可读、可删、可审计的状态；
- 训练：修改模型参数，难以逐条定位和删除；
- 上下文：本次推理实际看到的 token；
- 工具状态：环境中的文件、数据库或业务对象，只有被跨会话读取并纳入 agent 知识体系时才构成记忆。

## 0.3 生命周期：五个动作，一条闭环

[CoALA 中文译文](../../docs/coala-zh.md) 的决策循环可以写成：

```text
propose → evaluate → select → retrieve / reason / learn → execute
```

审计时给每个动作加日志：提议了什么、评估依据、选中了什么、检索到哪些 memory、学习/写入了什么、最终执行了什么。这样才可区分“没有记忆”“检索没找到”“找到了但没注入”“注入了但模型没用”。

```text
消息 / 轨迹 / 文档
        │
        ▼
      写入 ──► 组织 ──► 检索 ──► 使用 ──► 回答 / 行动
        ▲        │        │        │             │
        │        │        │        │             │
        └────────┴────────┴────────┴─────────────┘
                    治理：隔离 / 时间 / 失效 / 遗忘 / 审计
```

每个动作都要产生可验证的输出：

| 动作 | 输入 | 输出 | 关键契约 |
|---|---|---|---|
| 写入 | 原始消息、工具结果、外部事件 | 记忆单元与来源 | 幂等、顺序、失败不半写入 |
| 组织 | 记忆单元 | chunk、索引、元数据、关系 | 可重建、版本可追踪 |
| 检索 | 当前 query 与 scope | 候选集与分数/名次 | 不越权、可解释、预算受控 |
| 使用 | 候选集 | 最终注入上下文 | 去重、排序、截断、带来源 |
| 治理 | 新证据、删除请求、时间流逝 | 更新、失效、归档或删除 | 不误删、可审计、可恢复 |

**治理不是最后补上的功能，它贯穿所有动作。** 例如检索时的用户过滤属于治理，写入时的事实有效期也属于治理。

## 0.4 四种记忆类型

沿用 CoALA 和 LangGraph 的划分：

| 类型 | 内容 | 典型单元 | 示例 | 常见错误 |
|---|---|---|---|---|
| 工作记忆 | 当前决策周期中的活跃变量 | 消息窗口、草稿、当前计划 | 当前需求、未完成步骤 | 把临时猜测写成长期偏好 |
| 短期记忆 | 在有限时间或范围内可恢复的状态 | checkpoint、会话缓存、近邻消息 | 恢复当前任务 | 仅因持久化就称为跨会话语义记忆 |
| 情景记忆 | 发生过什么 | episode、原始消息、工具轨迹 | 上次报错、用户原话 | 只存摘要，无法回溯证据 |
| 语义记忆 | 知道什么事实、偏好、关系 | fact、entity、edge、profile | 用户时区、项目依赖 | 把过期事实当永久真理 |
| 程序记忆 | 怎么做 | rule、skill、playbook、prompt | 部署步骤、编码规范 | 把一次成功路径固化成通用规则 |

### semantic memory 与 semantic search

这两个词经常混淆：

- **semantic memory**：记忆的**内容类型**，指事实、概念、偏好和关系；
- **semantic search**：记忆的**检索方法**，通常用 embedding 找语义相似内容。

一个系统可以只有原始聊天记录，但使用 semantic search；也可以抽取了事实，却用关键词或 SQL 查询。两者没有必然关系。

### 类型不是存储介质

“向量记忆”“图记忆”描述的是组织方式，不是记忆类型。同一份用户偏好可以同时存在于原文、fact 和向量索引中；关键是它们如何同步、冲突和溯源。

## 0.5 四层外部知识结构

Anthropic 在《The components of agent memory》中把外部记忆分成四层。它是该文的工程框架，不是所有系统必须遵循的唯一分类：

| 层 | 内容 | 作用 | 主要风险 |
|---|---|---|---|
| Transcripts | 原始对话、工具调用、执行结果 | 可追溯的事实依据 | 噪声多、体积大 |
| Memory notes | agent 写的经验、规则、结论 | 跨会话复用 | 摘要漂移、错误固化 |
| Memory representations | wiki、索引、交叉链接 | 组织大量知识，便于导航 | 链接陈旧、重复维护 |
| Injected context | 每次会话主动加载的少量内容 | 减少重复检索 | 预算失控、错误被无条件信任 |

可以把它理解成一条加工链：

```text
Transcripts ──抽取/总结──► Memory notes ──组织──► Representations
     │                                                   │
     └────────────────────── 检索 / 选择 ────────────────┘
                                                         ▼
                                                   Injected context
```

### 记录如何跨层流动

每条派生记录至少保留：

```text
source → derived_from → version → promoted_from
```

例如：

```text
user message
  → extracted preference note
  → linked representation
  → promoted into always-on injected context
```

每个箭头都可能出错。错误笔记被晋升后，会在每次会话中重复出现。人工纠正必须沿链路传播：更新笔记、刷新表示、失效旧注入，而不是只改一处界面文本。

### InsightMem 的位置

[InsightMem 机制审计](../../wiki/insightmem.md) 主要实现：

- Transcripts：完整保存消息、chunk 和来源跨度；
- Representations：source view、代码展开 view、embedding 与 RRF 排序；
- Injected context 的候选准备：返回有限、可解释的原文证据。

它**没有实现** Memory notes 的事实抽取、长期整合、时间失效和自动遗忘。因此它是很好的“存储与检索参考实现”，不是完整记忆生命周期的唯一样板。

## 0.6 四个必须分清的边界

| 边界 | A | B | 判断方法 |
|---|---|---|---|
| 上下文 vs 记忆 | 本次推理可见的 token | 下次还能读取的外部状态 | 清空会话后是否仍存在 |
| Compaction vs 记忆 | 为继续当前会话而压缩 | 为跨会话复用而保存 | 压缩结果是否只服务于当前窗口 |
| RAG vs 记忆 | 通常检索静态知识库 | 从交互经验中持续获得并更新 | 数据是否来自 agent 自身经验 |
| 训练 vs 记忆 | 修改参数 | 修改外部状态 | 是否能逐条读取、纠正和删除 |

一个系统可以同时包含它们。例如 RAG 引擎可以检索 memory notes；checkpoint 可以持久化工作记忆；compaction 也可以把摘要写入长期存储。**判断依据是目的、生命周期和契约，而不是组件名字。**

## 0.7 记忆系统的七个质量属性

学完任何框架，都用这张表评估，而不是只数功能：

| 属性 | 核心问题 | 可测指标 |
|---|---|---|
| 保真度 | 写入后是否丢失关键细节 | 约束保留率、字段错误率 |
| 覆盖度 | 该找的信息是否能召回 | Recall@k、查询类型覆盖 |
| 新鲜度 | 新事实是否及时取代旧事实 | 更新延迟、旧事实误用率 |
| 隔离性 | 是否只读取授权范围 | 跨用户/租户泄漏测试 |
| 可解释性 | 结果能否追溯到来源 | 来源覆盖率、证据跨度正确率 |
| 可控性 | 能否纠正、失效、删除和审计 | 删除完整性、回滚成功率 |
| 成本与确定性 | token、延迟、存储是否可接受且可复现 | p50/p95、每查询成本、重复运行一致性 |

这些属性会互相牵制：

- 全量保存提高保真度，但增加检索噪声和成本；
- 摘要降低 token，但可能丢失约束；
- 图提升多跳能力，但增加抽取和运维成本；
- 自动遗忘降低容量，却可能误删未来需要的信息。

架构设计不是寻找“最强策略”，而是在明确任务下做可测量的取舍。

### 失败传播链

记忆错误通常沿以下链路影响回答：

```text
遗漏 / 错误 / 过时 / 串扰
  → 写入
  → 索引与检索
  → 候选选择
  → 注入上下文
  → 回答或行动
```

调试时先定位故障层：

| 现象 | 可能原因 | 验证方法 |
|---|---|---|
| 记忆库里没有 | 未写入、抽取遗漏、写入失败 | 查原始日志与写入状态 |
| 库里有但未召回 | 索引陈旧、查询不匹配、候选深度不足 | 绕过检索直接读取 |
| 召回了但未注入 | 过滤、预算截断、去重误删 | 查候选到 prompt 的 trace |
| 注入了但用错 | prompt 冲突、模型误读、旧事实未失效 | 固定上下文做对照 |
| 其他用户可见 | scope 过滤缺失 | 双用户哨兵测试 |

因此 `Recall@5` 高不等于答案正确；写入、检索、使用和治理必须分别评测。

### 四层消融

用同一组查询分别关闭或替换四层：

| 实验 | 能回答什么 |
|---|---|
| 无记忆 | 模型自身基线 |
| 只有 Transcripts | 原文检索是否足够 |
| 加入 Memory notes | 提炼是否减少噪声、是否引入偏差 |
| 加入 Representations | 索引/链接是否提升覆盖 |
| 改变 Injected context | 预算、排序和摘要如何影响最终答案 |

同时记录准确率、约束保留率、token、p50/p95 延迟和失败样本，不能只报一个平均分。

## 0.8 八种策略为什么不是分类

[八种记忆策略导读](strategy-overview.md)介绍全量、滑动窗口、相关性过滤、摘要、向量、图谱、分层和类 OS。它们适合建立直觉，但混合了不同维度：

- 全量、摘要：写入与表示；
- 窗口、向量、图谱：检索与上下文；
- 相关性过滤：治理或查询过滤；
- 分层、类 OS：组合架构。

学习时始终问：**这个策略改变了五个动作中的哪一个？是否改变存储？原始证据是否仍可恢复？**

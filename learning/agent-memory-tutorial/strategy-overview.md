## 0. 这篇导读怎么用

这篇导读把 Datawhale 的[《一文全解析：AI 智能体 8 种常见的记忆策略与技术实现》](https://mp.weixin.qq.com/s/nojzkY-dEnMZ99T17M9wZA)放进现有教程。原文发表于 2025-08-11，标注来源为“AI大模型应用实践 / 秋山墨客”，末尾引用了 [Fareed Khan 的 GitHub 项目](https://github.com/FareedKhan-dev/optimize-ai-agent-memory)。

先记住三个定位：

1. **它是二手教学导览，不是权威记忆分类。**
2. **原仓库介绍 9 种策略，中文文章整理为 8 种，不是逐条翻译。**
3. **示例主要用来建立直觉，没有系统性 benchmark，也不能直接当生产代码。**

正确用法是：先借它认识八种工程思路，再回到本教程的写入、检索、使用和治理章节，判断每种策略到底解决了哪个问题。

## 1. 先拆开四个维度

“八种记忆策略”看起来并列，其实不在同一维度上：

| 维度 | 要回答的问题 | 文章中的相关策略 |
|---|---|---|
| 记忆类型 | 存的是原文事件、事实关系，还是操作规则 | 全量、向量、图谱背后的内容类型 |
| 写入与表示 | 原样保存、提炼摘要，还是抽取结构 | 全量、摘要、图谱 |
| 检索与上下文 | 最近几轮、语义相近，还是沿关系查询 | 滑动窗口、向量、图谱、类 OS |
| 治理与组合 | 低分内容是否淘汰，多个模块如何协作 | 相关性过滤、分层、类 OS |

因此，下面四组区别比策略名称更重要：

- **保存全部历史 ≠ 每次把全部历史注入上下文。** 前者是存储策略，后者是上下文策略。
- **semantic search ≠ semantic memory。** 向量检索只是找相似内容，不保证抽取出正确事实。
- **查询时过滤 ≠ 删除记忆。** 过滤只影响本次返回；删除会改变以后还能否恢复。
- **Page In/Out ≠ 完整虚拟内存。** 它是上下文与外部存储协作的类比，不包含页表、地址翻译和系统级颠簸控制。

## 2. 八种策略分别解决什么

### 2.1 全量记忆：保留证据，不一定全部注入

**做法**：把每轮用户输入和智能体输出完整保存；最简单版本还会把全部历史重新交给模型。

**适合**：短对话、调试、需要逐字回溯的编码或合规场景。

**主要问题**：

- 历史增长后，token 成本、延迟和噪声同步增加；
- 超过上下文窗口后，最早内容仍可能被截断；
- “存得全”不意味着模型能有效利用全部内容。

**与 InsightMem 的关系**：它采用“全量持久化 + 按查询检索”，而不是“全量注入”。原始消息、chunk、索引和 embedding 都保留，Search 只返回有限证据。实现见 [InsightMem 机制审计](../../wiki/insightmem.md)。

### 2.2 滑动窗口：用可预测预算换取舍

**做法**：只保留最近 N 轮或最近若干 token，新消息进入时移除最旧内容。

**适合**：短会话、FAQ、对早期依赖较弱任务中的活动上下文。

**主要问题**：

- 窗口外的内容可能永久丢失；
- 按轮数计算不一定能控制 token，因为单轮长度差异很大；
- 粗暴截断可能拆开 tool call 与 tool result，破坏执行语义。

**实践要点**：系统提示、工具定义、关键约束和未完成工具调用通常不应被窗口随意裁掉。MemGPT 的 FIFO 队列是更完整的上下文管理案例，见 [MemGPT 精读](../../docs/papers-zh/01-foundations.md)。

### 2.3 相关性过滤：先区分“过滤”与“淘汰”

文章中的做法是：给记忆打重要性或相关性分数，容量超限时删除最低分内容。评分可参考主题相关性、最近提及频率和用户偏好等。

这里必须区分两种操作：

| 操作 | 发生时机 | 是否改变存储 |
|---|---|---|
| 查询时过滤 | 本次检索或注入上下文 | 否 |
| 低分淘汰 | 写入或容量管理 | 是 |

**适合**：信息密集、需要主动控制记忆容量的场景。

**主要问题**：分数难以校准，当前不相关不代表未来无用；误删通常不可逆。工程上可优先考虑降权、分层或归档，并为淘汰记录理由。

**与 InsightMem 的关系**：它的过程叙述过滤发生在查询时；被过滤内容仍参与 BM25 统计和 RRF 排名，不会被删除。详见 [三路检索与证据选择](../../wiki/insightmem-retrieval.md)。

### 2.4 摘要/压缩：减少注入量，但保留原始依据

**做法**：把较早的对话总结成较短表示，再与近期原文一起注入。常见形式是“运行摘要 + 最近窗口”。

**适合**：长对话、只需要保留主线偏好的个人助手。

**主要问题**：

- 摘要可能遗漏约束、数字、否定词和因果条件；
- 多轮递归摘要会累积漂移；
- 摘要调用增加写入成本和延迟；
- 只保留摘要时，后续无法核对原始依据。

**实践要点**：把摘要当派生表示，不当唯一事实源；保留原文、来源跨度和摘要版本。评测时除了 token 数，还要测关键约束保留率和错误事实率。

### 2.5 向量数据库：一种检索表示，不是记忆类型

**做法**：把文本嵌入成向量，查询时用 dense similarity 召回 top-k 片段。

**适合**：跨会话语义召回、 paraphrasing、模糊偏好查询。

**主要问题**：

- embedding 质量决定召回上限；
- 精确标识符、错误码、路径和罕见词容易漏召回；
- 缺少 metadata filter 时，可能跨越错误用户、时间或项目范围；
- “存进向量库”不等于完成事实抽取和更新。

**实践要点**：生产系统通常需要词法 + 向量的混合检索，并固定模型身份、维度、归一化方式和过滤条件。InsightMem 已实现原始 BM25、代码展开 BM25 与 dense cosine 三路召回。

### 2.6 知识图谱：显式关系带来多跳能力

**做法**：从对话中抽取实体、属性和关系，形成三元组或带时间信息的边，再沿关系查询。

**适合**：企业知识、订单与客户关系、科研概念关系等需要多跳推理的任务。

**主要问题**：

- 抽取错误会变成结构化的错误事实；
- 实体消歧、关系合并和有效期维护成本高；
- 图不自动解决模糊语义匹配；
- 多跳结果需要来源和置信度，否则只是更长的错误链。

**实践要点**：图与向量通常互补：向量找入口，图沿关系扩展。现有 [现代系统精读](../../docs/papers-zh/03-systems.md) 已覆盖 Graphiti、HippoRAG 等更完整的实现。

### 2.7 分层记忆：组合多种策略，而不是新存储介质

文章中的分层记忆通常是：

```text
工作记忆：最近几轮，滑动窗口
长期记忆：重要事实或摘要，可检索
提升机制：关键词或 LLM 判断哪些内容进入长期层
读取：近期上下文 + 长期召回
```

**适合**：同时需要即时响应和跨会话 recall 的个人助手、客服或教学 agent。

**主要问题**：提升规则、写入时机、召回预算和层间一致性都会增加调试难度。关键词“记住”“总是”只能作为弱信号，不能证明信息重要或长期有效。

更系统的分层还应区分原始事件、提炼事实、操作规则，以及它们各自的更新和删除路径，参见 [概念地图](../../wiki/agent-memory.md)。

### 2.8 类 OS 内存管理：上下文与外部存储的换入换出

**做法**：把活动上下文当作 RAM，把旧轮次转存到外部存储；查询需要旧信息时，再检索并 Page In。

**适合**：长生命周期、需要随时回溯但活动上下文很小的任务型 agent。

**主要问题**：

- “缺页”判断和召回可能漏掉真正需要的内容；
- 换入内容没有预算控制，会再次撑爆上下文；
- 外部存储需要持久化、隔离、幂等和删除能力；
- 文章示例没有实现完整的页管理或颠簸保护。

MemGPT 的主上下文、外部上下文、队列管理、递归摘要和函数执行更接近完整机制，见 [MemGPT 与 Letta](../../wiki/memgpt-letta.md)。

## 3. 八种策略如何组合

实际系统通常不会只选一种。三个常见组合是：

| 场景 | 组合方式 | 重点评测 |
|---|---|---|
| 编码证据助手 | 全量原文 + chunk + 词法/向量混合检索 + 证据去重 | Recall@k、重复霸榜、关键约束遗漏 |
| 长期个人助手 | 近期窗口 + 事实/偏好抽取 + metadata filter + 向量召回 | 旧事实误用、跨用户泄漏、更新延迟 |
| 研究助理 | 原文档案 + 分层摘要 + 实体图 + 向量入口 | 来源可追溯、多跳正确率、抽取错误率 |

选择策略时，先问五个问题：

1. 什么信息丢了就找不回来？
2. 原文、摘要和事实是否都需要保留？
3. 查询更依赖近期顺序、语义相似还是显式关系？
4. 谁来决定删除、过期和提升？
5. token、延迟、存储和 LLM 调用成本分别花在哪一步？

## 4. 读文章示例代码时要注意

文章的代码用于表达思路，不是可直接运行的参考实现：

- `concat_all`、`embed`、`evaluate`、`summarize` 等辅助函数没有完整实现；
- 摘要示例在清空列表后又取最近轮次，会丢失本想保留的近期对话；
- 相关性示例按 `order` 排序，但没有完整定义该字段；
- 类 OS 示例只是拼接关键词命中内容，没有真正的换入预算或页管理；
- 所有示例都省略了持久化、用户隔离、幂等、并发、失败恢复和审计。

学习时应把“理解机制”和“验证代码”分开：先画出状态变化，再用本教程的实验方法补 baseline、失败案例和成本数字。

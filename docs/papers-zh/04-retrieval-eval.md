## HippoRAG: Neurobiologically Inspired Long-Term Memory for Large Language Models

**作者**：Bernal Jiménez Gutiérrez, Yiheng Shu, Yu Gu, Michihiro Yasunaga, Yu Su
**时间**：2024（arXiv:2405.14831v3）
**一句话**：借海马索引理论，把 LLM、知识图谱和个性化 PageRank 组合起来，做便宜又快的多跳检索。

### 摘要（译文）

为了在恶劣、多变的环境中生存，哺乳动物大脑进化出存储大量世界知识、持续整合新信息并避免灾难性遗忘的能力。尽管 LLM 取得了 impressive 的成就，即使有 RAG，它们仍难以在预训练后高效、有效地整合大量新经验。本文提出 **HippoRAG**：一种受人类长期记忆的海马索引理论启发的检索框架，用于在新经验上实现更深、更高效的知识整合。HippoRAG 协同编排 LLM、知识图谱和个性化 PageRank 算法，模拟人类记忆中皮层和海马的不同角色。作者在多跳问答上与现有 RAG 方法比较，结果显示最高提升 20%；HippoRAG 的单步检索达到与 IRCoT 等迭代检索相当或更好的性能，同时便宜 10–30 倍、快 6–13 倍；把 HippoRAG 集成到 IRCoT 还能带来进一步提升。最后，作者展示了该方法能处理现有方法无法触及的新场景。

### 核心设计

- **知识图谱**：从文档抽取实体和关系，构建图；
- **个性化 PageRank（PPR）**：从查询实体出发，在图上传播相关性，找到多跳邻居；
- **海马/皮层类比**：LLM 负责语义处理，图 + PPR 负责索引和关联召回；
- **单步检索**：一次图传播替代多轮迭代检索。

### 实验与结论

多跳 QA 上最高提升 20%；相比 IRCoT 便宜 10–30 倍、快 6–13 倍；与 IRCoT 结合还能进一步提升（论文自报）。

### 局限

- 图构建依赖实体/关系抽取，抽取错误会传播；
- 图更新和维护有成本；
- 主要在静态文档语料上验证，动态对话记忆的适用性需进一步研究。

### 为什么读

如果你的查询需要“A 通过 B 关联到 C”，单靠向量和词法不够，HippoRAG 展示了图 + PPR 的性价比。读它重点看：图怎么建、PPR 怎么用、为什么能替代多轮检索。

## From Local to Global: A Graph RAG Approach to Query-Focused Summarization

**作者**：Darren Edge, Ha Trinh, Newman Cheng, Joshua Bradley, Alex Chao, Apurva Mody, Steven Truitt, Dasha Metropolitansky, Robert Osazuwa Ness, Jonathan Larson
**时间**：2024（arXiv:2404.16130v2，CC BY）
**一句话**：用实体知识图谱 + 社区摘要回答“整个语料的主题是什么”这类全局问题。

### 摘要（译文）

用 RAG 从外部知识源检索相关信息，可以让 LLM 回答私有或未见文档集合上的问题。但 RAG 在面向整个文本语料的全局问题上会失败，例如“这个数据集的主要主题是什么？”——这本质上是查询聚焦摘要（QFS）任务，而不是显式检索任务。此前的 QFS 方法又无法扩展到典型 RAG 系统索引的文本量。为结合两类方法的优势，作者提出 **GraphRAG**：一种基于图的私有文本语料问答方法，能随用户问题的通用性和源文本数量扩展。该方法用 LLM 分两阶段构建图索引：先从源文档派生实体知识图谱，再为紧密相关实体组预生成社区摘要。给定问题时，每个社区摘要生成部分回答，再把所有部分回答汇总成最终回答。在 100 万 token 规模数据集的全局 sensemaking 问题上，GraphRAG 在答案的全面性和多样性上显著优于传统 RAG 基线。

### 核心设计

- **实体知识图谱**：LLM 抽取实体和关系；
- **社区检测与摘要**：把紧密相关实体分组，预生成社区摘要；
- **查询时 map-reduce**：每个社区摘要生成部分回答，最后汇总；
- **面向全局问题**：不是找某一段，而是覆盖整个语料的主题和关系。

### 实验与结论

100 万 token 规模；在全面性和多样性上优于传统 RAG（论文自报）。具体评分口径见原文。

### 局限

- 索引阶段 LLM 成本高，构建慢；
- 面向静态语料，不处理时间失效和对话更新；
- 对局部事实问题不一定优于普通 RAG；
- 社区摘要可能丢失细节或引入概括错误。

### 为什么读

它和 Zep/Graphiti 形成对照：GraphRAG 是“静态语料的全局理解”，Graphiti 是“动态对话的时序事实”。读它重点看社区摘要和 map-reduce 查询，而不是把它当通用记忆系统。

## LongMemEval: Benchmarking Chat Assistants on Long-Term Interactive Memory

**作者**：Di Wu, Hongwei Wang, Wenhao Yu, Yuwei Zhang, Kai-Wei Chang, Dong Yu
**时间**：2024-10 首版；arXiv:2410.10813v2，2025-03-04；ICLR 2025
**许可**：论文 CC BY 4.0
**规模**：500 道人工策展问题；LongMemEvalS 约 115k token/题；LongMemEvalM 为 500 个会话、约 1.5M token/题
**一句话**：把“记住用户”拆成可测量的五种能力，再用统一键值存储视角检查索引、检索和阅读分别在哪里失败。

> 数字口径：以下实验数值均为**论文自报**。同一 benchmark 内的不同设置也不能混为同一口径：商业系统 pilot、长上下文 pilot、Oracle 阅读实验和 LongMemEvalM 检索实验的条件各不相同。本文不与 LoCoMo 或其他 benchmark 横向比较分数。

### 摘要（译文）

近期，LLM 驱动的聊天助手已加入记忆组件，用于跟踪用户与助手之间的聊天历史，以提供更准确、更个性化的回复。然而，其在持续交互中的长期记忆能力仍缺乏充分研究。本文提出 **LongMemEval**，一个评测聊天助手五种核心长期记忆能力的综合 benchmark：**信息抽取、多会话推理、时间推理、知识更新和弃答**。500 道精心策展的问题被嵌入长度可自由扩展的用户—助手聊天历史。论文摘要概括称，商业聊天助手和长上下文 LLM 在跨持续交互记忆信息时，准确率下降约 30%。

作者进一步提出统一框架，把长期记忆设计分解为**索引、检索、阅读**三个阶段。基于关键实验发现，优化包括：调整价值粒度并分解会话；用事实增强索引键；通过时间感知查询扩展缩小检索范围。大量实验表明，这些优化同时改善记忆召回和下游问答。作者公开了 benchmark 与代码，希望为更个性化、更可靠的对话 AI 提供资源和设计指导。

### 1 引言：评测的不是“能读多长”，而是“能否持续记住”

LLM 能处理多种自然语言任务，但心理疏导、秘书助理等场景依赖长期积累的用户背景与偏好。忽略这些信息会降低回答的准确性和满意度。长期记忆要求系统不仅能保存历史，还能在之后**回忆、更新并推理**；压缩、索引和检索正是当前商业与开源系统采用的主要手段。

论文指出既有对话评测的两类缺口：

1. **交互形态不真实**：不少数据只有人—人对话，或缺少任务导向交互；后者的长输入、长回复尤其考验记忆。许多历史长度固定且只有几千 token，难以随系统能力增长持续加压。
2. **能力覆盖不完整**：既有工作对跨众多会话综合、利用时间元数据、记住助手提供的信息、处理用户信息更新等能力考察不足。

LongMemEval 因此把每个问题放进一条**带时间戳、可扩展、按顺序在线摄入**的历史。系统必须先处理全部会话，再回答最后的问题。标准设置为约 115k token 的 **LongMemEvalS** 和 500 个会话、约 1.5M token 的 **LongMemEvalM**。这不是把一句话藏进长文的大海捞针，而是把答案分散到多个扩展证据会话中，考查检索与综合。

### 3.1 问题形式化

一个评测实例是四元组 `(S, q, t_q, a)`：

- `S = [(t₁, S₁), …, (t_N, S_N)]`：从早到晚排列的历史会话；`Sᵢ` 是一次多轮用户—助手交互，`tᵢ` 是其时间戳。
- 每个会话可继续拆成**轮次（round）**：一条用户消息加一条助手回复。
- 测试时，系统按顺序逐个接收 `S`；问题 `q` 在全部历史之后提出，提问日期满足 `t_q > t_N`。
- `a` 通常是简短答案；开放题则用自然语言 rubric 描述 preferred answer，即什么样的回答可接受。

这个定义同时固定了**信息在哪里、何时发生、何时提问、什么算答对**。时间既是 session 元数据，也可能出现在用户措辞中；两者都是时间推理的考查对象。

### 3.2 Benchmark 构建

构建分三步：人工构造问题与证据；LLM 模拟证据会话后由人工修改；测试时把证据会话插入无关历史。题目难度与历史长度因此可以分别控制。

#### 164 属性本体：控制用户背景的覆盖面

作者人工建立 **164 个用户属性**，分为五类：

| 类别 | 含义 |
|---|---|
| lifestyle | 生活方式 |
| belongings | 所有物 |
| life events | 人生事件 |
| situational context | 情境背景 |
| demographic information | 人口统计信息 |

对每个属性，使用 LLM 生成一段聚焦该属性的用户背景，其中包含多项生活经历与近期事实。属性本体控制“可以问什么”，背景段落则为后续出题提供素材；它不是从真实用户画像中直接采样。

#### 问题策展：LLM 提案，人工定难度与答案证据

流程如下：

1. 随机抽取一段属性背景；
2. 让 LLM 提出若干种子 `(问题, 答案)`；
3. 人类专家过滤并重写问题，因为自动生成题通常缺乏深度和多样性；
4. 人工把答案拆成一条或多条**证据陈述（evidence statement）**，必要时附时间戳。

附录称，每类问题约生成 1000 个候选题，最终留存率约 5%。时间推理、多会话推理和单会话偏好还使用 GPT-4o 辅助提案，但最终筛选与编辑仍由人工完成。可见，LLM 主要扩大候选 pool，真正决定题目质量的是人工策展。

#### 证据会话：让事实间接出现，而不是直接报答案

每条证据陈述单独嵌入一个任务导向会话。模拟时，用户 LLM 被要求间接传达信息。例如，不直接说“上个月买了新车”，而是询问车险，在对话中自然带出买车事实。这样，系统必须识别并保存未被明确强调的个人细节。

随后人工检查并编辑，保证：

- 证据确实出现，且没有泄漏同一问题的其他证据；
- 证据分布在会话不同位置；
- 表达自然、口语化，尤其避免 LLM 把时间说法写得过于正式；
- 会话能自然结束，并标注证据位置。

附录给出更多实现细节：模拟会话最多 10 轮；约 70% 的会话经过人工编辑。多数问题需要多个证据会话，**最多 6 个**。涉及时间的题目还会人工为证据会话和问题补上时间戳。

#### 历史编译：把证据插入可延长的不相干历史

对每道题，采样若干无关用户—助手会话，与证据会话一起打乱，再为所有会话分配合理时间戳。无关会话有三个来源：

- 基于其他不冲突属性模拟的会话；
- ShareGPT；
- UltraChat。

附录给出的采样配比为 **25% ShareGPT、25% UltraChat、50% 模拟会话**。若证据之间有顺序要求，打乱后再调整其相对次序。时间戳沿历史顺序随机分配；若证据已有预设时间，就以它为锚确定前后无关会话的时间范围，否则使用 2023 年 5 月中的随机日期。

这套设计让无关历史在话题和格式上与证据会话接近，同时尽量避免冲突信息破坏答案。它类似 needle-in-a-haystack，但检索对象是多个扩展会话，且需要综合，而非只定位一个短句。

#### S / M / Oracle：三个不同用途的设置

| 设置 | 历史规模 | 用途 |
|---|---|---|
| LongMemEvalS | 约 115k token/题；正文称约 50 个会话 | 考查长上下文直接阅读与在线记忆 |
| LongMemEvalM | 500 个会话，约 1.5M token/题 | 考查大规模记忆检索与 RAG |
| Oracle | 只保留证据会话 | 提供理想检索上界，分离检索错误与阅读错误 |

S 与 M 不是同一模型在同一上下文窗口下的两种截断长度；M 主要配合外部记忆检索。Oracle 也不是完整产品测试，它回答的是：**假设证据已经全部找齐，模型能否用好？**

### 七种问题类型与五种核心能力

五种能力是**信息抽取（IE）、多会话推理（MR）、时间推理（TR）、知识更新（KU）、弃答（ABS）**。七种问题类型把它们落到具体任务上：

| 问题类型 | 考什么 | 对应能力 |
|---|---|---|
| `single-session-user` | 回忆单个会话中用户提到的信息 | 信息抽取 |
| `single-session-assistant` | 回忆单个会话中助手提到的信息 | 信息抽取 |
| `single-session-preference` | 利用用户信息生成个性化回答 | 信息抽取 + 个性化运用 |
| `multi-session` | 跨至少两个会话聚合、比较用户信息 | 多会话推理 |
| `knowledge-update` | 识别生活状态变化，采用更新后的信息 | 知识更新 |
| `temporal-reasoning` | 结合时间戳与显式时间表达推理 | 时间推理 |
| `abstention` | 面对错误前提或历史未提供的信息，不编造答案 | 弃答 |

弃答题不是全新领域，而是从上述类型中抽取 **30 题**，改成 false-premise 问题。它直接检验系统能否区分“历史没有答案”与“我需要找一个答案”。

### 3.3 评测指标

#### 问答：用 LLM 判断答案是否可接受

正确答案可能有短语、改写或推理过程等多种形式，精确匹配容易误判。因此论文使用 **gpt-4o-2024-08-06**，通过 OpenAI API 按问题类型提示评分。正文报告 evaluator 与人类专家的整体一致率**超过 97%**；附录进一步说明，各任务设置下一致率为 **90% 或以上**，开放式的单会话偏好与弃答题偏离略大。

因此，QA 分数不是字面匹配率，而是**特定 judge prompt 下的可接受回答比例**。复现时应固定 judge 模型、prompt 和数据版本。

#### 记忆召回：检查答案证据是否进入 top-k

数据集人工标注了答案位置。若系统暴露检索结果，就可计算：

- **Recall@k**：前 k 个结果是否覆盖应有的答案位置；
- **NDCG@k**：在考虑排序位置后，相关证据是否靠前。

`k` 是系统取回的项目数。按会话或按轮次标注，会得到不同粒度；官方代码同时提供 `answer_session_ids` 与带 `has_answer: true` 的轮次标签。弃答题通常没有可定位的 gold answer，官方检索评测脚本会跳过这 30 题。

**Recall 与 QA 必须分开看**：证据找齐仍可能读错；极少数情况下只找到更新后的事实也可能答对，却会被要求同时覆盖旧信息的严格召回标注判为未完全召回。

### 3.4 Pilot study：现有系统为什么不够

#### 商业在线记忆系统

ChatGPT 与 Coze 的 memory 功能只能通过网页使用。作者随机选 **97 题**，为每题构造 **3–6 个会话、约比 LongMemEvalS 短 10 倍**的历史。人工标注者逐会话、逐轮与系统交互，最后在新会话提问。评测时间为 **2024 年 8 月前两周**。

对照设置为 GPT-4o 直接读取完整历史的 **Offline Reading**。以下准确率均为**论文自报**：

| 系统 / 设置 | LLM | Accuracy |
|---|---|---:|
| Offline Reading | GPT-4o | 91.84% |
| ChatGPT | GPT-4o | 57.73% |
| ChatGPT | GPT-4o-mini | 71.13% |
| Coze | GPT-4o | 32.99% |
| Coze | GPT-3.5-turbo | 24.74% |

论文图注称，同样使用 GPT-4o 时，ChatGPT 与 Coze 相对离线阅读分别下降 **37%** 和 **64%**；这是相对降幅，不是 37 与 64 个百分点。人工分析发现，ChatGPT 倾向在后续聊天中覆盖关键信息，Coze 则常漏记间接提供的用户信息。这个 pilot 说明：记住若干孤立事实，不等于具备可靠的长期记忆。

#### 长上下文 LLM

作者在 LongMemEvalS 的约 115k token 历史上评测 GPT-4o、Llama 3.1 Instruct 70B/8B、Phi-3 128k Instruct 14B、Phi-3.5 Mini Instruct 4B，并与只给证据会话的 Oracle 比较。下表保留正文图 3 的全部数值；**下降幅度是相对 Oracle 的降幅**。

| 模型 | 规模 | Oracle（无 CoN） | S（无 CoN） | 下降 | Oracle（CoN） | S（CoN） | 下降 |
|---|---:|---:|---:|---:|---:|---:|---:|
| GPT-4o | — | 87.0% | 60.6% | 30.3% | 92.4% | 64.0% | 30.7% |
| Llama 3.1 Instruct | 70B | 74.4% | 33.4% | 55.1% | 84.8% | 28.6% | 66.3% |
| Llama 3.1 Instruct | 8B | 71.0% | 45.4% | 36.1% | 71.0% | 42.0% | 40.8% |
| Phi-3 128k Instruct | 14B | 70.2% | 38.0% | 45.9% | 72.2% | 34.4% | 52.4% |
| Phi-3.5 Mini Instruct | 4B | 66.0% | 34.2% | 48.1% | 65.2% | 32.4% | 50.3% |

摘要与引言将这一现象概括为约 **30%–60%** 的下降；完整 pilot 表中最差为 **66.3%**。两种表述应保留各自语境，不能把摘要数字当成所有设置的上限。加入 Chain-of-Note 也不保证提升：Llama 3.1 70B 的 S 分数反而从 33.4% 降至 28.6%。

这些结果只证明“直接读完整 S 历史”仍有明显损失，不证明扩大上下文永远无效。论文的判断更具体：历史会持续增长，不能假设当前最强的长上下文模型可以替代显式记忆机制。

### 4 统一视角：键值存储、三个阶段、四个控制点

#### 4.1 长期记忆作为大规模键值存储

论文把记忆写成 `[(k₁,v₁), (k₂,v₂), …]`：

- **key** 可以异构，既可离散也可连续；离散 key 可以是句子、段落、事实或实体，连续 key 可以是模型内部表示；
- **value** 是实际保存、之后供阅读的内容，允许重复。

这个抽象能容纳向量检索、文本检索、压缩记忆和不同业务系统。重点不是强行使用某一种数据库，而是明确每个阶段存什么、按什么找、找到后怎么用。

| 阶段 | 输入 | 操作 | 输出 |
|---|---|---|---|
| 索引 indexing | 带时间戳的历史会话 | 把一个会话转成一个或多个 key-value item | 可检索的记忆项 |
| 检索 retrieval | 用户问题 | 构造查询，取回最相关的 k 项 | 候选记忆集合 |
| 阅读 reading | 问题 + 候选记忆 | 由 LLM 阅读、抽取、推理 | 最终回答 |

#### 4.2 四个控制点

1. **Value：存下来的内容是什么，粒度多细？**
   - 整会话太长且跨多个主题，不利于检索和阅读；
   - 压成摘要或用户事实节省 token，但可能丢失细节；
   - 需要比较整会话、单轮次、摘要与事实，而不是默认“越短越好”。

2. **Key：凭什么找到这个 value？**
   - 直接把 value 当 key 是强基线，但只有部分内容与问题相关；
   - 可从 value 抽取摘要、关键词、用户事实和带时间事件，扩展检索入口；
   - 关键是**增加通路**，不是用压缩文本替换原文。

3. **Query：如何把问题变成合适的搜索？**
   - 普通相似度检索难以处理“上周推荐的餐厅”等相对时间；
   - 可把事件日期写入索引，并从问题推断时间范围；
   - 时间过滤会缩小搜索空间，但推断错误也会误删证据。

4. **Reading strategy：证据找齐后，如何让模型用好？**
   - 多会话问题常需要很长的检索上下文；
   - 可先用 Chain-of-Note 从每条记忆中摘取相关信息，再基于简短 notes 推理；
   - 结构化格式帮助模型区分记忆项、元数据与问题。

三阶段是执行顺序，四控制点是各阶段可调的设计变量；二者不是一一对应关系。

### 5 实验：优化到底改善了什么

#### 5.1 实验设置

- 主要 reader：GPT-4o、Llama 3.1 70B Instruct、Llama 3.1 8B Instruct；
- retriever：1.5B 的 Stella V5 稠密检索模型；
- 索引抽取：Llama 3.1 8B Instruct，用于摘要、关键词、用户事实和带时间事件；
- 当 session 或 round 本身作为 key 时，只保留用户侧话语；
- 阅读时按时间戳排序检索项，帮助维持时间一致性；
- 5.2–5.4 默认使用 Chain-of-Note 与 JSON 格式，避免阅读策略成为混淆变量。

#### 5.2 Value：轮次通常优于整会话，但继续压成事实会丢信息

论文在 **LongMemEvalM** 上做预算感知比较：

- 对 GPT-4o，把会话分解为轮次显著改善阅读；对 Llama 3.1 8B，表现与不分解会话相近；
- 用摘要或用户事实替代会话 / 轮次，虽节省 token，却因信息丢失损害总体 QA；
- 例外是多会话推理：事实分解能稳定提升表现。作者假设，跨会话抽取同类事实形成更统一、简化的格式，便于检索和阅读；
- 最佳检索 token 预算取决于 reader：Llama 3.1 8B 在超过约 **3k 检索 token** 后明显下降，GPT-4o 在超过 **20k token** 后仍继续改善。

正文图 5 只给出定性结论，未列出逐柱数值，因此这里不估读柱高，也不把“显著”改写成未经报告的绝对提升。可迁移的结论是：**先用轮次控制粒度，再按问题类型决定是否值得抽取事实**，而不是把所有记忆一律压成最短文本。

#### 5.3 Key：原文与用户事实拼接，优于单独替换

论文比较 `K = V`、`K = fact`、`K = keyphrase`、`K = V + fact`、`K = V + keyphrase`，会话粒度下还比较 summary。单独使用摘要、关键词或事实，并没有整体提升召回；作者认为稠密 retriever 已能处理长文本语义。

有效做法是 document expansion：把抽取信息与原 value 拼接形成 key。正文概括为：使用用户事实扩展后，**Recall@k 平均提高 9.4%，最终 QA 平均提高 5.4%**。这里的 `%` 按论文原口径保留；正文未明确说明该汇总是相对百分比还是绝对百分点，不应擅自换算。

以下是表 3 中轮次 / 会话粒度、原始键与事实扩展键的对照，数值均为**论文自报**：

| Value | Key | Recall@5 | NDCG@5 | Recall@10 | NDCG@10 |
|---|---|---:|---:|---:|---:|
| Round | `K = V` | 0.582 | 0.481 | 0.692 | 0.512 |
| Round | `K = V + fact` | 0.644 | 0.498 | 0.784 | 0.536 |
| Session | `K = V` | 0.706 | 0.617 | 0.783 | 0.638 |
| Session | `K = V + fact` | 0.732 | 0.620 | 0.862 | 0.652 |

| Value | Key | GPT-4o QA@5 / @10 | Llama 3.1 70B QA@5 / @10 | Llama 3.1 8B QA@5 / @10 |
|---|---|---:|---:|---:|
| Round | `K = V` | 0.615 / 0.670 | 0.600 / 0.624 | 0.518 / 0.534 |
| Round | `K = V + fact` | 0.657 / 0.720 | 0.638 / 0.682 | 0.566 / 0.572 |
| Session | `K = V` | 0.670 / 0.676 | 0.592 / 0.570 | 0.524 / 0.464 |
| Session | `K = V + fact` | 0.714 / 0.700 | 0.588 / 0.584 | 0.530 / 0.490 |

表 3 也提醒我们：扩展键不是每个 reader、每个 top-k 都提升。例如会话粒度的 Llama 3.1 70B 与 8B，QA@10 都略降。论文还比较了检索后融合不同通路的排名，效果不如索引阶段拼接，因此推荐先做 key 扩展，再考虑复杂融合。

#### 5.4 Query：时间感知扩展缩小范围，但依赖准确的时间抽取

方法分两侧：

- **索引**：抽取可推断日期的事件，保存为 `date + event`，按事件日期增加索引入口；
- **查询**：对确实含时间范围的问题，让 LLM 根据提问日期推断 `start + end`，过滤无关记忆；没有时间引用时应返回 `N/A`。

正文报告：使用较强 LLM 做查询扩展时，轮次粒度的召回平均提高 **11.3%**，会话粒度平均提高 **6.8%**；与事实扩展键同时使用仍有一致收益。该 `%` 同样保留论文汇总口径。

表 4 的时间推理子集原始数值如下，每格为 **Recall / NDCG**：

| Key 设置 | Session@5 | Session@10 | Round@5 | Round@10 |
|---|---:|---:|---:|---:|
| `K = V` | 0.639 / 0.630 | 0.651 / 0.707 | 0.421 / 0.462 | 0.499 / 0.511 |
| `K = V` + GPT-4o 扩展 | 0.654 / 0.660 | 0.707 / 0.679 | 0.451 / 0.565 | 0.495 / 0.538 |
| `K = V` + Llama 3.1 8B 扩展 | 0.624 / 0.627 | 0.647 / 0.692 | 0.384 / 0.448 | 0.489 / 0.488 |
| `K = V + fact` | 0.684 / 0.688 | 0.721 / 0.782 | 0.489 / 0.500 | 0.550 / 0.598 |
| `K = V + fact` + GPT-4o 扩展 | 0.722 / 0.732 | 0.797 / 0.758 | 0.526 / 0.548 | 0.722 / 0.669 |
| `K = V + fact` + Llama 3.1 8B 扩展 | 0.677 / 0.688 | 0.711 / 0.744 | 0.481 / 0.532 | 0.570 / 0.647 |

并非每项都上升：例如会话粒度、事实扩展键下，NDCG@10 从 0.782 变为 0.758；Llama 3.1 8B 在多项设置下反而下降。附录的错误样例显示，它常在没有时间引用时臆造范围，从而提前剪掉正确证据。GPT-4o 更能拒绝这种抽取。工程上应把“是否启用时间过滤”本身当成一个需要评测的决策，而不是默认所有查询都应过滤。

#### 5.5 Reading：Chain-of-Note 与结构化格式解决“找齐仍答错”

阅读优化有两项：

1. 用 **JSON** 表示检索项，让模型清楚区分记忆数据；
2. 用 **Chain-of-Note（CoN）** 要求模型先逐项提取相关信息，再基于 notes 推理，把长上下文阅读拆成“摘取细节”和“基于精简材料推理”两步。

在 Oracle 设置下，即只提供证据会话时，论文报告三种 reader LLM 的 QA 最高提升 **10 个绝对百分点**。关键交互是：

- 不用 CoN 时，JSON 不总是优于自然语言；
- 使用 CoN 时，JSON 对各种能力的 reader 都稳定有帮助；
- CoN + JSON 是图 6 的四种组合中最佳方案。

图 6 没有逐点数值表，因此只保留论文报告的“最高 10 个绝对百分点”，不补造各模型分数。Oracle 提升说明阅读策略独立于召回质量；不能把全部错误都归因于 retriever。

#### 5.6 错误归因：检索与阅读都要单独度量

附录使用轮次 value、用户事实扩展键、CoN 阅读、Stella V5 1.5B、top-10 与 JSON  prompt：

- **15%–19%** 的实例是“检索正确、生成错误”，占全部错误实例的 **40%–50%**；reader 越弱，比例越高；
- 约 **90%** 的正确回答依赖正确检索；
- 其余约 10% 主要出现在知识更新题：只找到更新后的知识，没有找到更新前信息。严格召回判为失败，但模型仍可能答对。

这组数字支持把评测拆成 Recall@k、NDCG@k、QA 和错误类型，而不是只报一个总分。

### 6 结论

LongMemEval 用 500 道人工策展问题评测信息抽取、多会话推理、时间推理、知识更新和弃答。商业在线记忆与长上下文直接阅读的实验表明，现有系统在持续增长的历史中仍有明显损失。

统一键值存储视角进一步把改进点定位到价值粒度、索引键、查询构造和阅读策略。论文的总体答案不是“把上下文再扩大”或“把记忆压得更短”，而是：

- 用轮次而不是整会话控制默认粒度；
- 保留原文，同时用用户事实扩展 key；
- 显式保存事件时间，并谨慎扩展时间查询；
- 找齐证据后，仍要通过结构化阅读与 CoN 提高利用率。

这些优化共同改善召回与下游 QA，但收益依赖 reader、预算、粒度和问题类型，不能当作无条件成立的默认配置。

### 局限与阅读边界

论文没有独立的 Limitations 小节；以下是根据其数据构建、实验设置和伦理声明归纳的边界，不作为作者逐条自述：

- **历史是编译的，不是自然留存的**：证据由 LLM 模拟、人工修改，无关会话按固定来源采样，并刻意避免属性冲突。真实产品中的噪声、冲突和删除行为更复杂。
- **规模不等于真实分布**：500 题提供标准化比较，但属性本体主要围绕个人生活事实；不能直接外推到编码、多模态或开放环境操作。
- **商业结果是时间快照**：97 题 pilot 使用 3–6 个会话，且产品接口与行为会变化，不能视为当前商业系统的固定排名。
- **judge 与 prompt 影响分数**：QA 使用 GPT-4o 自动评判；开放式偏好与弃答题的一致性低于整体数字。answerer、阅读格式和预算都必须随分数报告。
- **数据版本会影响复现**：官方仓库在 2025 年 9 月发布了进一步清理历史的 `longmemeval-cleaned`。论文原始数字与清理版数据上的结果不应无说明地混用。
- **更新与弃答覆盖仍有限**：知识更新主要检验显式信息变化；弃答由 30 个错误前提题构成，不能代表所有幻觉或安全问题。
- **记忆治理未被框架充分展开**：伦理声明指出，存储个人信息可能泄漏，缺少记忆删除操作会损害信任，恶意内容也可能被写入记忆库。基准分数不能替代权限、删除、审计和内容 moderation。

### 对 InsightMem 的工程启示

以下是基于论文的工程引申，**不是 LongMemEval 对 InsightMem 的实测结论**：

1. **把原始证据与检索表示分开。** 当前 [coding service](../../src/insightmem/coding/service.py) 已把消息切成带来源 span 的 chunk，并由 [evidence assembler](../../src/insightmem/coding/evidence.py) 返回原文切片。新增摘要或用户事实时，应作为辅助 key / view 指回同一 span，而不是替换原始证据。这与“扩展 key，不丢 value”一致。
2. **轮次是待验证的候选粒度，不是唯一答案。** 当前实现按消息切 chunk；LongMemEval 的 round 是“用户消息 + 助手回复”。对聊天数据可增加请求内轮次视图，与现有消息级粒度做对照；对编码轨迹则不能机械套用，因为一次工具调用、结果和后续推理需要不同的上下文边界。
3. **扩展索引通路，并保留可重建性。** 可在 `index_views` 中加入用户事实、关键短语或事件视图。现有 build / embedding fingerprint 已能标识索引配置；增加抽取器或 prompt 时，也应纳入版本标识，避免新旧视图混检。
4. **时间戳不能只用于展示。** 当前消息保存 `timestamp_ms`，检索结果也返回 `created_at`，但 search 不解析问题时间范围，也不做时间过滤。若要支持“上次修改前”等问题，应区分消息时间与事件发生时间，并显式测试“无时间引用时不过滤”和“弱模型误抽范围时少剪证据”。
5. **阅读策略属于调用方契约。** 当前 `/add` 与 `/search` 只负责写入和检索，不生成答案。下游可用 JSON 呈现 `id、role、kind、created_at、content`，先摘证据再作答；同时按时间排序需要由 reader 明确执行，不能假设 `/search` 的相关性排序已经保持时间顺序。
6. **知识更新与弃答需要额外状态。** 当前存储强调不可变来源和幂等写入，不等于维护“新事实取代旧事实”。可增加带生效时间的 assertion 层，保留新旧证据链接；没有命中证据时应允许“不知道”，不能把检索分低直接当成事实为假。
7. **建立分层评测，而不是只报 QA。** 对聊天适配层可分别报告七类问题的 Recall@k、NDCG@k、QA、阅读错误、延迟和检索 token 预算。InsightMem 的编码记忆评测应使用与编码任务对齐的数据，不能把 LongMemEval 分数直接当作编码能力证明。
8. **把删除与审计纳入长期记忆。** 原始 span、派生事实、索引视图和缓存应能一致失效；用户删除请求不能只删向量而留下摘要或事实副本。

### 与 LongMemEval-V2 的关系

官方 V1 仓库已指向 **LongMemEval-V2: Evaluating Long-Term Agent Memory Toward Experienced Colleagues**。两者共享“从长期历史中找回经验并支持回答”的目标，但评测对象与能力轴发生转移：

- V1 聚焦用户—助手聊天历史，核心是个人事实、偏好、更新、时间与弃答；
- V2 聚焦 web / enterprise agent 的多模态执行轨迹，考查静态状态、动态状态、工作流知识、环境陷阱与前提感知；系统需返回紧凑证据，并同时关注答案准确性与查询延迟。

因此，V2 不是 V1 的简单扩长版，也不能沿用同一套能力标签、数据或分数。V1 的“索引 / 检索 / 阅读”和“原始证据可溯源”仍有参考价值；InsightMem 的编码轨迹在形态上更接近 agent history，但领域、任务和指标尚未对齐，不能据此宣称通过 V2。详细译读见 [LongMemEval-V2 中文译读与精读](05-longmemeval-v2.md)。这里只说明关系，不比较两个 benchmark 的分数。

## Evaluating Very Long-Term Conversational Memory of LLM Agents（LoCoMo）

**作者**：Adyasha Maharana, Dong-Ho Lee, Sergey Tulyakov, Mohit Bansal, Francesco Barbieri, Yuwei Fang
**时间**：2024（arXiv:2402.17753v1，CC BY-NC-SA）
**一句话**：构造平均 300 轮、跨 35 个会话的超长期对话，评测 LLM 的长期记忆、时间因果和多模态理解。

### 摘要（译文）

现有长期开放域对话工作最多只评估 5 个会话内的回复。尽管长上下文 LLM 和 RAG 有进展，它们在超长期对话中的有效性仍未探索。为填补空白，作者提出一个机器-人类流水线：利用基于 LLM 的 agent 架构，把对话建立在人设和时间事件图上，生成高质量超长期对话；每个 agent 还能分享和回应图像。生成的对话经人工标注者验证和编辑，以保证长程一致性和对事件图的落地。用该流水线，作者收集了 **LoCoMo**：一个超长期对话数据集，每个平均 300 轮、9K token，跨最多 35 个会话。基于 LoCoMo，作者提出一个综合评测 benchmark，覆盖问答、事件摘要和多模态对话生成。实验表明，LLM 在理解长对话、长程时间和因果动态方面存在挑战；长上下文 LLM 或 RAG 能带来改进，但仍显著落后于人类。

### 数据与任务

- 平均 300 轮、9K token、最多 35 个会话；
- 人设 + 时间事件图 + 图像分享；
- 任务：问答、事件摘要、多模态对话生成；
- 人工验证长程一致性。

### 实验与结论

长上下文和 RAG 有提升，但仍低于人类；LLM 在长程时间/因果理解上明显吃力（论文自报）。

### 局限

- 对话是合成的，虽经人工验证，仍不等于真实用户分布；
- 主要是英文；
- 评测规模和任务类型有限；
- 论文许可是 CC BY-NC-SA。

### 为什么读

它是“超长期对话记忆”最常用的评测之一。读它重点看：数据怎么构造、问题类型、为什么长上下文仍然不够。

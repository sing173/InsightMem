# LLM Wiki

一种使用 LLM 构建个人知识库的模式。

这是一个理念文件，设计为复制粘贴到你自己的 LLM Agent（例如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达高阶理念，但你的 Agent 将与你合作构建具体细节。

## 核心思想

大多数人与 LLM 和文档的交互方式类似 RAG：你上传一组文件，LLM 在查询时检索相关片段，并生成答案。这确实可行，但 LLM 在每个问题上都要从头重新发现知识。没有积累。问一个需要综合五份文档的细微问题，LLM 每次都要寻找并拼接相关片段。什么都没有建立起来。NotebookLM、ChatGPT 文件上传和大多数 RAG 系统都是这样工作的。

这里的想法不同。LLM **逐步构建和维护一个持久化的 Wiki**——一个结构化的、相互链接的 markdown 文件集合，位于你和原始源文档之间。当你添加新源时，LLM 不仅仅是索引它供以后检索。它阅读源文档，提取关键信息，并将其整合到现有 Wiki 中——更新实体页面、修订主题摘要、记录新数据何时与旧主张矛盾、加强或挑战不断演进的综合。知识只编译一次，然后*保持最新*，而不是在每次查询时重新推导。

这是关键区别：**Wiki 是一个持久的、复合的工件。** 交叉引用已经就位。矛盾已被标记。综合已反映你阅读过的所有内容。Wiki 随你添加的每个源和提出的每个问题而变得更加丰富。

你从不（或很少）自己编写 Wiki——LLM 编写和维护所有内容。你的职责是策展源文档、探索和提出正确的问题。LLM 处理所有苦差事——总结、交叉引用、归档和记账，这些使知识库随时间真正有用。实际上，我让 LLM Agent 在一侧运行，Obsidian 在另一侧打开。LLM 根据我们的对话进行编辑，我实时浏览结果——跟随链接、查看图形视图、阅读更新的页面。Obsidian 是 IDE；LLM 是程序员；Wiki 是代码库。

这可以应用于许多不同场景。一些示例：

- **个人**：追踪你自己的目标、健康、心理、自我提升——归档日记、文章、播客笔记，并随着时间建立关于自己的结构化图景。
- **研究**：深入钻研一个持续数周或数月的主题——阅读论文、文章、报告，并逐步构建一个包含不断演进论点的全面 Wiki。
- **阅读书籍**：归档每章内容，为角色、主题、情节线索及其联系建立页面。读完后，你会得到一个丰富的 companion wiki。想想像 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page) 这样的粉丝 Wiki——数千个相互链接的页面涵盖角色、地点、事件、语言，由志愿者社区多年来构建。随着阅读，你可以个人构建类似的东西，LLM 负责所有交叉引用和维护工作。
- **商业/团队**：由 LLM 维护的内部 Wiki，由 Slack 对话、会议记录、项目文档、客户电话提供。可能有人员在循环中审查更新。Wiki 保持最新，因为 LLM 处理没人想做的维护工作。
- **竞争分析、尽职调查、旅行计划、课程笔记、爱好深挖**——任何你随时间积累知识并希望其组织有序而非 scattered 的场景。

## 架构

有三层：

**原始源文档** —— 你策展的源文档集合。文章、论文、图片、数据文件。这些是**不可变的**——LLM 从中读取但从不修改它们。这是你的真实来源。

**Wiki** —— 一个 LLM 生成的 markdown 文件目录。摘要、实体页面、概念页面、比较、概述、综合。LLM 完全拥有这一层。它创建页面、在新源到达时更新它们、维护交叉引用、保持一切一致。你阅读它；LLM 编写它。

**模式（Schema）** —— 一个文档（例如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM Wiki 是如何结构的、约定是什么，以及在摄入源文档、回答问题或维护 Wiki 时应遵循什么工作流。这是关键配置文件——它使 LLM 成为纪律严明的 Wiki 维护者，而非通用聊天机器人。你和 LLM 随时间共同演进它，随着你发现哪些对你的域有效。

## 操作

**摄入（Ingest）。** 你将一个新源放入原始集合，并告诉 LLM 处理它。示例流程：LLM 阅读源文档，与你讨论关键要点，在 Wiki 中编写摘要页面，更新索引，更新 Wiki 中相关的实体和概念页面，并向日志追加条目。单个源可能触及 10-15 个 Wiki 页面。我个人偏好一次摄入一个源并保持参与——我阅读摘要、检查更新、指导 LLM 应该强调什么。但也可以批量摄入多个源且监督较少。由你发展适合你风格的工作流，并在模式中记录以供未来会话使用。

**查询（Query）。** 你针对 Wiki 提问。LLM 搜索相关页面，阅读它们，并用引用综合答案。答案可以采取不同形式——取决于问题：markdown 页面、比较表、幻灯片 deck（Marp）、图表（matplotlib）、画布（canvas）。重要见解：**你询问的答案可以 filed back into the wiki as new pages。** 你要求的比较、分析、你发现的联系——这些是有价值的，不应消失在聊天历史中。这样你的探索像摄入的源一样在知识库中复合。

**检查（Lint）。** 定期让 LLM 对 Wiki 进行健康检查。查找：页面间的矛盾、较新源已 superseded 的过时声明、没有入链的孤立页面、提到但缺乏自己页面的重要概念、缺失的交叉引用、可以用网络搜索填充的数据缺口。LLM 擅长建议新问题调查和新源寻找。这使 Wiki 在增长时保持健康。

## 索引和日志

两个特殊文件帮助 LLM（和你）在 Wiki 增长时导航。它们服务不同目的：

**index.md** 是面向内容的。它是 Wiki 中所有内容的目录——每个页面都列出链接、一行摘要、可选元数据如日期或源计数。按类别组织（实体、概念、源等）。LLM 在每次摄入时更新它。在回答查询时，LLM 首先读取索引以查找相关页面，然后深入阅读。这在中等规模（~100 个源，~几百个页面）出奇地有效，避免了基于嵌入的 RAG 基础设施需求。

**log.md** 是时序的。它是一个仅追加的记录，记录发生了什么以及何时发生——摄入、查询、检查通过。一个有用技巧：如果每个条目以一致前缀开头（例如 `## [2026-04-02] ingest | Article Title`），日志可以用简单 unix 工具解析——`grep "^## \[" log.md | tail -5` 给你最后 5 个条目。日志给你 Wiki 演进的时间线，帮助 LLM 理解最近做了什么。

## 可选：CLI 工具

某个时刻你可能想要构建小工具，帮助 LLM 更高效地操作 Wiki。一个 Wiki 页面的搜索引擎是最明显的——小规模时索引文件足够，但随着 Wiki 增长你需要 proper search。[qmd](https://github.com/tobi/qmd) 是不错选择：它是本地 markdown 文件搜索引擎，混合 BM25/vector search 和 LLM 重排序，全部设备端运行。它有 CLI（所以 LLM 可以 shell out 到它）和 MCP 服务器（所以 LLM 可以将其作为原生工具使用）。你也可以自己构建更简单的——随着需求出现，LLM 可以帮助你 vibe-code 一个 naive search 脚本。

## 提示和技巧

- **Obsidian Web Clipper** 是浏览器扩展，将网页文章转换为 markdown。对快速将源放入原始集合非常有用。
- **本地下载图片。** 在 Obsidian 设置 → 文件和链接中，将"附件文件夹路径"设为固定目录（例如 `raw/assets/`）。然后在设置 → 热键中，搜索"Download"找到"Download attachments for current file"并绑定热键（例如 Ctrl+Shift+D）。剪辑文章后，按下热键，所有图片下载到本地磁盘。这是可选的但有用——它让 LLM 可以直接查看和引用图片，而不是依赖可能失效的 URL。注意 LLM 不能一次性原生读取带内联图片的 markdown——workaround 是让 LLM 先阅读文本，然后单独查看部分或所有引用图片以获得额外上下文。这有点笨拙但足够有效。
- **Obsidian 的图形视图** 是查看 Wiki 形状的最佳方式——什么连接到什么，哪些页面是 hub，哪些是 orphan。
- **Marp** 是基于 markdown 的幻灯片 deck 格式。Obsidian 有相关插件。从 Wiki 内容直接生成演示文稿有用。
- **Dataview** 是 Obsidian 插件，对页面 frontmatter 运行查询。如果你的 LLM 为 Wiki 页面添加 YAML frontmatter（标签、日期、源计数），Dataview 可以生成动态表格和列表。
- Wiki 只是 markdown 文件的 git 仓库。你免费获得版本历史、分支和协作。

## 为什么这有效

维护知识库的苦差事不是阅读或思考——它是记账。更新交叉引用、保持摘要最新、记录新数据何时与旧主张矛盾、跨数十个页面维护一致性。人类放弃 Wiki 是因为维护负担增长比价值更快。LLM 不会无聊，不会忘记更新交叉引用，一次可以触及 15 个文件。Wiki 保持维护，因为维护成本接近零。

人类的工作是策展源文档、指导分析、提出好问题、思考这一切的含义。LLM 的工作是其他所有事情。

这个想法在精神上类似于 Vannevar Bush 的 Memex（1945）——一个个人、策展的知识库，文档之间有联想 trail。Bush 的愿景更接近这个，而不是网络成为的样子：私人的、积极策展的，文档间连接与文档本身一样有价值。他无法解决的部分是谁来做维护。LLM 处理那个。

## 注

本文档故意抽象。它描述理念，而非具体实现。确切的目录结构、模式约定、页面格式、工具——所有这些将取决于你的域、你的偏好、你的 LLM 选择。上面提到的所有内容都是可选和模块化的——挑选有用的，忽略没用的。例如：你的源可能只是文本，所以你根本不需要图片处理。你的 Wiki 可能足够小，索引文件就够了，不需要搜索引擎。你可能不在乎幻灯片 deck，只想要 markdown 页面。你可能想要完全不同的输出格式集合。使用此的正确方式是将其分享给你的 LLM Agent，并一起构建适合你需求的版本。这份文件的唯一任务是传达模式。你的 LLM 可以处理其余部分。
